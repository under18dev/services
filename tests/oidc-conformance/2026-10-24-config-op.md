## 結論

**Discovery ドキュメントの中身は、RS256 の 1 点を除いて適合している。**

- **仕様との意図的な差 1 件**: `id_token_signing_alg_values_supported` に **RS256 が無い**。OIDC Discovery 1.0 §3 は RS256 を MUST としている → **#112 → 仕様書 決定 10 で「ES256 のみを維持し、意図的に非適合とする」と確定**。

  実行時点では実バグとして起票したが、判断の結果 **仕様を満たさないことを選んだ**項目になった。決定 10 の理由は、(1) 2 つの alg を広告することは RP に選択させること＝alg の多様性の導入であり、仕様書 §9 の「署名アルゴリズム固定」に正面から逆行する、(2) Discovery が RS256 を MUST にしているのは「任意の RP が任意の OP のトークンを検証できる」相互運用の保証のためだが、§1.2 で外部 Developer Portal を非目標としクライアントは内部管理のみなので **その保証の受益者が存在しない**、(3) runbook §4 のローテーション手順は 1 鍵 1 alg 前提で、RSA を足すと鍵運用が 2 系統になる。**将来 RP を外部へ開く場合（#39）は再検討する。**

- **環境由来 7 件**: すべて `http` スキームに対する指摘。`wrangler dev` を平文 HTTP で動かしているため。本番は `ISSUER=https://auth.under18.dev` なので該当しない

### 環境由来の 7 件が他を隠していないこと

スイートは最初の失敗で止まらず **45 ステップすべてを実行している**。スキーマ検証（`ValidateServerMetadataAgainstSchema`）、未知パラメータの検査、JWKS の取得と解析、`response_types` / `grant_types` / `claims` / `scopes` / `subject_types` の検査はいずれも実行されて SUCCESS している。

`wrangler dev --local-protocol https` も試したが、**自己署名証明書をスイートのコンテナが拒否する**（`curl` が exit 000）ため、スキーマ検査の目的では平文のまま流して切り分けた。本番 URL に対して流す際にこの 7 件は消えるはずで、**それは本番デプロイ後に確認する**。

## 副次的に確認できたこと

`EnsureJwksHasNoPrivateOrSymmetricKeyMaterial` が SUCCESS している。**JWKS に秘密鍵が出ていないことを、自前のテストではなく外部のスイートが確認した。**
`signing-key.mjs` のコメントが警告している「`public_jwk` に `d` を入れると JWKS 経由で秘密鍵を世界へ配る」という事故が起きていないことの、独立した裏付けになる。

## 再現手順

### 1. スイートを起動する

**Maven ビルドは不要。** 公式のビルド済みイメージがリポジトリ内の compose ファイルで参照されている。

```sh
git clone https://gitlab.com/openid/conformance-suite.git
cd conformance-suite
git checkout release-v5.3.3
IMAGE_TAG=release-v5.3.3 podman compose -f docker-compose-prebuilt.yml up -d
# https://localhost.emobix.co.uk:8443 で待ち受ける（証明書は正規のもの）
```

**Podman で動かすこと。** このマシンでは Docker Desktop を停止している
（VM が CPU 10 個 / メモリ 8GB を確保したまま応答しなくなったため）。
`host.docker.internal` は Podman でもそのまま解決されるので、
`wrangler dev` を参照する箇所の書き換えは要らない。

**同じ手順を Docker と Podman の両方で流し、結果が完全に一致することを
確認した。** SUCCESS 21 / FAILURE 8 / INFO 7 という件数も、FAILURE した
チェックの集合も同一だった。

### 2. 流す先を用意する

```sh
pnpm db:migrate:local
pnpm --filter @u18/auth-worker key:generate --apply-local
# 出力の SIGNING_KEY_JWK / SIGNING_KEY_KID を apps/auth-worker/.dev.vars へ
# IP_HASH_PEPPER も入れる

cd apps/auth-worker
pnpm exec wrangler dev --ip 0.0.0.0 --port 8790 \
  --var ISSUER:http://host.docker.internal:8790
```

- **`--ip 0.0.0.0` が要る。** 既定の localhost 束縛ではコンテナから届かない
- **`ISSUER` を `host.docker.internal` にする。** Discovery が広告する URL をスイートが辿るので、コンテナから解決できる名前でなければならない
- **ポートは 8787 を避ける。** 他のセッションの `wrangler dev` と衝突した。衝突しても `0.0.0.0` と `127.0.0.1` の両方が LISTEN になるだけで**エラーにならず、別の Worker に当たる**ので気づきにくい

### 3. プランを作って流す

```sh
curl -sk -X POST \
  "https://localhost.emobix.co.uk:8443/api/plan?planName=oidcc-config-certification-test-plan" \
  -H 'Content-Type: application/json' -d '{
    "alias": "u18-local",
    "description": "u18 Identity - Config OP (local wrangler dev)",
    "server": { "discoveryUrl": "http://host.docker.internal:8790/.well-known/openid-configuration" },
    "client": { "client_id": "u18-conformance-probe", "client_secret": "unused-for-config-op" }
  }'
# -> {"id":"<planId>"}

curl -sk -X POST "https://localhost.emobix.co.uk:8443/api/runner?test=oidcc-discovery-endpoint-verification&plan=<planId>"
# -> {"id":"<testId>"}

curl -sk "https://localhost.emobix.co.uk:8443/api/info/<testId>"   # status / result
curl -sk "https://localhost.emobix.co.uk:8443/api/log/<testId>"    # 全ログ
```

**`variant` クエリは渡さないこと。** このプランは variant を自分で固定しているため、渡すと
`Variant 'server_metadata' has been set by user, but test plan already sets this variant` で拒否される。
