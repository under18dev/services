## 1. スコープと前提

### 1.1 対象に含むもの

| 対象             | 実体                                                                                                                                                                                                                                        | 備考                                                                                                                 |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| auth-worker      | `apps/auth-worker/`                                                                                                                                                                                                                         | OIDC 公開 HTTP、アカウント API、内部 RPC Entrypoint                                                                  |
| dashboard-worker | `apps/dashboard-worker/`                                                                                                                                                                                                                    | アカウント UI の BFF。Identity D1 への binding を持たない                                                            |
| Identity D1      | `packages/db/src/schema/*.ts` のスキーマが載る `IDENTITY_DB`                                                                                                                                                                                | `apps/auth-worker/wrangler.jsonc` でのみ binding される                                                              |
| RPC 境界         | `IdentityRPC`（`apps/auth-worker/src/presentation/rpc/identity.entrypoint.ts`）と `RpcIdentityGateway`（`apps/dashboard-worker/src/infrastructure/rpc/identity.gateway.ts`）                                                                | 契約は `packages/contracts/src/identity.ts`                                                                          |
| 共有パッケージ   | `packages/contracts`、`packages/domain`、`packages/db`                                                                                                                                                                                      | 型・契約・純粋ロジックのみ。セッション Cookie 名は `packages/contracts/src/session-cookie.ts` で両 Worker が共有する |
| Workers Secrets  | `SIGNING_KEY_JWK` / `SIGNING_KEY_KID` / `IP_HASH_PEPPER`（`apps/auth-worker/wrangler.jsonc` のコメントに列挙）。**`EMAIL_API_KEY` は存在しない** —— メール送信は Cloudflare Email Sending のバインディング経由で、API キーを持たない（#35） | 値はリポジトリに存在しない                                                                                           |

### 1.2 対象に含まないもの

- ~~**NFC 連携（仕様書 §10 / Phase 4）**~~ — **対象に含める**（#159）。`nfc-worker` は
  実装され本番で稼働している（#30 / #31、PR #92）。脅威は §3.7 で扱う（N-1〜N-9）。
- **外部 IdP（Google / GitHub 等）によるソーシャルログイン**：仕様書 §1.2 の非目標。
- **SAML**：仕様書 §1.2 の非目標。
- **外部開発者向け Developer Portal**：OAuth クライアント登録は内部管理のみ（`oauth_clients` を
  運用者が直接登録する前提）。
- **Cloudflare プラットフォーム自体の侵害**（Workers ランタイムの脱獄、D1 の基盤的な不正アクセス）：
  信頼の基点として前提に置く。
- **エンドユーザー端末のマルウェア・OS レベルの侵害**：パスキーの秘密鍵は認証器内に留まる前提。

### 1.3 信頼境界

```text
[1] ブラウザ / 外部 OIDC クライアント
        |  HTTPS（完全に信頼できない公開境界）
        v
[2] auth-worker 公開 HTTP  (apps/auth-worker/src/presentation/http/)
        |
[3] auth-worker 内部 RPC   (apps/auth-worker/src/presentation/rpc/identity.entrypoint.ts)
        ^
        |  Service Binding（信頼の付与ではない）
[4] dashboard-worker / 将来の nfc-worker
        |
[5] Identity D1 + Workers Secrets（最重要資産。auth-worker だけが触れる）
```

境界ごとの前提を明示する。

**境界 A：ブラウザ ↔ auth-worker（公開・非信頼）**
リクエストの一切を信用しない。Cookie、ヘッダ、`Origin`、`User-Agent`、ボディ、クエリ、
すべて攻撃者が任意に制御できる。`apps/auth-worker/src/presentation/http/me.routes.ts` が
`userId` をパスやボディで受け取らず常に Cookie のセッションから導いているのは、この前提の帰結である。

**境界 B：dashboard-worker ↔ auth-worker（Service Binding。信頼の付与ではない）**
これが本書で最も強調すべき前提である。Service Binding は「公開 URL を持たない」という
到達性の制約にすぎず、**権限の委譲ではない**。`apps/dashboard-worker/wrangler.jsonc` の
`services[].entrypoint: "IdentityRPC"` が与えるのは `IdentityRPC` の **全メソッドを呼ぶ能力**
であって、「正しい引数で呼ぶ約束」ではない。したがって：

- dashboard-worker が侵害された場合、攻撃者は `getSession` / `getUserProfile` /
  `listSessions` / `revokeSession` を任意の引数で、任意の回数、呼び出せる。
- RPC が外部 HTTP を経由しないことは、入力検証・認可・監査を省略してよい理由にならない
  （仕様書 §2.2 設計原則 3、§9 補足）。`identity.entrypoint.ts` の各メソッドが冒頭で
  `safeParse` を通し、`userId` を呼び出し元の申告ではなくセッションから導いているのは
  この前提への対応である。
- 将来 `nfc-worker` を追加するときも、同じ `IdentityRPC` を共有せず、必要なメソッドだけを
  持つ別の Named Entrypoint を切る（仕様書 §4.2 の注記）。

**境界 C：auth-worker ↔ Identity D1 / Workers Secrets（最重要）**
`IDENTITY_DB` binding は `apps/auth-worker/wrangler.jsonc` にしか存在せず、
`apps/dashboard-worker/wrangler.jsonc` には意図的に D1 binding がない。署名秘密鍵は
`signing_key_metadata` に保存せず（`packages/db/src/schema/oauth.ts` の同テーブル定義コメント）、
Workers Secret に置く。auth-worker のコード実行権限または Secrets の読み取り権限を奪われた時点で
本システムの全セキュリティ保証が失われる。ここが単一障害点であることを前提に、
デプロイ権限と Secrets の管理は別途の運用統制（仕様書 §9 Infrastructure）に委ねる。

### 1.4 想定する攻撃者

| 攻撃者                                   | 能力                                                                           |
| ---------------------------------------- | ------------------------------------------------------------------------------ |
| 匿名のインターネット利用者               | 公開エンドポイントへの任意リクエスト、自動化、スクリプト                       |
| 登録済みの正規ユーザー（内部犯）         | 有効なセッションを 1 つ持ち、他人の資源へ横展開を試みる                        |
| 悪意ある / 侵害された OAuth クライアント | 正規の `client_id` を持ち、Redirect URI や PKCE の検証不備を突く               |
| 侵害された dashboard-worker              | `IdentityRPC` の全メソッドを任意引数で呼べる。D1 には触れない                  |
| 受動的なネットワーク観測者               | HTTPS 前提のため平文は見えないが、トラフィックのタイミング・サイズは観測しうる |
| D1 のダンプを入手した者                  | テーブルの全列を読める。Workers Secrets は読めない                             |

## 2. 資産

攻撃者が狙う対象を、価値の高い順に列挙する。

| #   | 資産                                          | 所在                                                                                             | 奪われたときの影響                                                                                                                                    |
| --- | --------------------------------------------- | ------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| A1  | **ID Token 署名秘密鍵**                       | Workers Secret `SIGNING_KEY_JWK`                                                                 | 任意の `sub` に対する ID Token を偽造でき、全 RP で全ユーザーに成りすませる。システム全体の信頼が失われ、鍵ローテーションと全 RP への周知が必要になる |
| A2  | **任意の `sub` の ID Token を発行させる能力** | `/oauth/token`（Phase 2）、`oauth_authorization_codes` の発行経路                                | A1 の鍵を得なくても、認可フローの欠陥（コード再利用、Redirect URI 迂回、PKCE 検証漏れ）があれば同じ結果に至る                                         |
| A3  | **セッショントークン（平文）**                | ブラウザ Cookie `__Host-u18_session` のみ。DB には SHA-256 ハッシュのみ（`sessions.token_hash`） | そのユーザーとして全操作が可能。最大 12 時間（`TokenLifetime.sessionMs`）                                                                             |
| A4  | **認可コード（平文）**                        | リダイレクト URL のクエリに 60 秒だけ存在。DB には `oauth_authorization_codes.code_hash` のみ    | PKCE なしなら即座にトークン交換が可能。PKCE S256 があれば `code_verifier` も必要                                                                      |
| A5  | **メール OTP（平文）**                        | 送信メール内のみ。DB には `email_challenges.code_hash` のみ                                      | パスワードレス認証の突破。6 桁なので総当たりへの耐性は試行上限に依存する                                                                              |
| A6  | **ユーザーのメールアドレス**                  | `users.primary_email`、`user_emails.email`                                                       | 未成年ユーザーを含むため、フィッシング・特定・嫌がらせの材料になる。仕様書 §9 Privacy が明示的に保護を要求                                            |
| A7  | **Access Token / Grant**                      | `oauth_tokens.token_hash`、`oauth_grants`                                                        | scope の範囲で UserInfo を読まれる。同意の偽造でユーザーの意図しないアプリへ情報が流れる                                                              |
| A8  | **WebAuthn Credential の公開鍵とカウンター**  | `passkeys.public_key` / `passkeys.counter`                                                       | 公開鍵自体は秘密ではないが、書き換えられるとクローン検出（カウンター巻き戻り検知）が無効化される                                                      |
| A9  | **IP ハッシュの pepper**                      | Workers Secret `IP_HASH_PEPPER`                                                                  | 漏洩すると `sessions.ip_hash` / `audit_logs.ip_hash` が IPv4 全空間の総当たりで元に戻り、匿名化が無効になる                                           |
| A10 | **監査ログの完全性**                          | `audit_logs`                                                                                     | 改竄・削除されると侵害の事後追跡が不可能になる                                                                                                        |
| A11 | **サービスの可用性**                          | auth-worker 全体                                                                                 | u18 の全サービスのログインが同時に止まる。単一障害点                                                                                                  |

**非資産（意図的に保持しない）**：学校名、生年月日、住所、電話番号、生 IP アドレス、パスワード。
`packages/db/src/schema/users.ts` の `users` テーブルは `username` / `displayName` /
`primaryEmail` / `emailVerified` / `status` のみを持ち、これらの属性の列を持たない。
「持たないデータは漏れない」という方針を実装レベルで固定している。

## 3. 脅威分析（STRIDE）

STRIDE（Spoofing / Tampering / Repudiation / Information Disclosure / Denial of Service /
Elevation of Privilege）を整理の枠として用いる。各脅威に ID を振り、§5 のチェックリストから参照する。

### 3.1 S — なりすまし（Spoofing）

#### S-1：認可コードの傍受とリプレイ

| 項目         | 内容                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 攻撃シナリオ | 攻撃者が Referer 漏洩、ブラウザ履歴、プロキシログ、あるいは悪意あるブラウザ拡張から、リダイレクト URL のクエリに載った `code` を取得する。被害者より先に `/oauth/token` へ提示してトークンを得る。あるいは被害者の交換が成功した直後に同じコードをもう一度提示し、二重に発行させようとする。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| 緩和策       | (1) PKCE S256 必須。`oauth_authorization_codes.code_challenge_method` は `{ enum: ["S256"] }` でスキーマレベルに固定され、`plain` を表現できない（`packages/db/src/schema/oauth.ts`）。Discovery も `code_challenge_methods_supported: ["S256"]` のみを公開する（`apps/auth-worker/src/presentation/http/oauth.routes.ts`）。コードを盗んでも `code_verifier` がなければ交換できない。(2) 単回交換。`oauth_authorization_codes.consumed_at` への条件付き UPDATE（`consumed_at IS NULL` を WHERE に含める）で、同時に 2 回来ても片方だけが行を更新する。同じ原子的更新のパターンは `apps/auth-worker/src/infrastructure/persistence/drizzle-session.repository.ts` の `revoke()` に既に実装されており（`and(eq(sessions.id, id), isNull(sessions.revokedAt))` + `.returning()` の件数判定）、認可コード側はこれを踏襲する。(3) 有効期間 60 秒（`TokenLifetime.authorizationCodeMs` — `apps/auth-worker/src/domain/services/token-lifetime.ts`）。(4) コードは平文で保存せず `code_hash` のみ（`secretHash()` — `packages/db/src/schema/_shared.ts`）。(5) 再利用を検出したら、そのコードから派生した `oauth_tokens` と `oauth_grants` を失効させ、`audit_logs` に `oauth.code.replayed` を記録する（イベント名は `packages/db/src/schema/audit.ts` のコメントに例示済み）。 |
| 現状         | **実装済み**（#15 / #16 / #19、PR #99）。`/oauth/authorize` と `/oauth/token` が動作し、**本番で稼働している**。認可コードは単回消費の条件付き UPDATE（`DrizzleAuthorizationCodeRepository.consume()`）で、同時交換の検証は実 D1 に対する `test/oauth-code-concurrency.test.ts` が行う（インメモリの fake では「同時」が作れないため別ファイルにしてある）。再利用を検出したら `oauth.code.replayed` を記録し、その grant のトークンを失効させる。PKCE S256 は必須（仕様書 §14.1 決定 9）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |

#### S-2：セッション固定（Session Fixation）

| 項目         | 内容                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 攻撃シナリオ | 攻撃者が自分で未認証のセッション Cookie を取得し、それを被害者のブラウザに何らかの手段（サブドメインからの Cookie 書き込み、レスポンススプリッティング）で植え付ける。被害者がそのセッションでログインを完了すると、攻撃者の手元にある同じトークンが認証済みセッションに昇格する。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| 緩和策       | (1) `__Host-` 接頭辞（`SESSION_COOKIE_NAME = "__Host-u18_session"` — `packages/contracts/src/session-cookie.ts`。auth-worker 側の `apps/auth-worker/src/presentation/http/session-cookie.ts` と dashboard-worker の `apps/dashboard-worker/src/index.ts` は、いずれもこの契約の `sessionCookieName(environment)` を呼んで名前を得る）。ブラウザは `__Host-` 付き Cookie に対し「Secure 必須・Path=/ 必須・Domain 属性禁止」を強制するため、サブドメインからの上書き経路が塞がれる。これは session fixation に対する最も効く構造的防御である。(2) 認証成功ごとに新しいセッション行を `DrizzleSessionRepository.create()` で作り、新しいトークンを発行する。既存セッションを認証済みに「昇格」させる経路をコード上に作らない。(3) ログイン前の匿名状態で `sessions` 行を作らない。 |
| 現状         | **実装済み**。`__Host-` 接頭辞と Cookie 属性は `session-cookie.ts` の `buildSessionCookie()` に実装済み （`HttpOnly`、`Secure`、`SameSite=Lax`、`Path=/`）。名前は共有契約（`packages/contracts`）に集約され、両 Worker が同じ値を見る。**未認証のセッションを発行する経路が無い**ので、固定の前提が成立しない —— Cookie は `IssueSessionUseCase` が本人確認後に初めて発行し、認証のたびに新しいトークンを作る（既存の行を昇格させない）。**本番で確認済み**: OTP 登録直後に `__Host-u18_session`（`Path=/; Max-Age=43199; HttpOnly; Secure; SameSite=Lax`）が発行され、ログアウト後は `Max-Age=0` で破棄される。ホスト構成は #33 で確定した（RR-11）                                                                                                                            |

#### S-3：WebAuthn のリプレイ / 認証器のクローン

| 項目         | 内容                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 攻撃シナリオ | 攻撃者が被害者の WebAuthn アサーション（`clientDataJSON` と署名）をネットワークまたは侵害された RP フロントエンドから取得し、後から同じものを `/api/auth/passkeys/login/verify` へ送る。あるいは認証器そのものが複製され、同じ Credential ID で並行して使われる。さらに、フィッシングサイトが自身のオリジンでアサーションを取得し、それを本物の auth-worker へ中継しようとする。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| 緩和策       | (1) Challenge の単回消費。`webauthn_challenges` テーブル（`packages/db/src/schema/auth.ts`）は `challenge` に `uniqueIndex`、`expiresAt`、`consumedAt` を持ち、options 発行時に保存して verify で消費する。サーバー側に保存せずクライアント申告の challenge を信じる実装はリプレイを防げない（同テーブルの定義コメントに明記）。有効期間は `TokenLifetime.webauthnChallengeMs`（5 分）。(2) サインカウンターの巻き戻り検出。`passkeys.counter` は認証のたびに単調増加するはずで、提示値が保存値以下なら Credential の複製を示唆するため拒否する。(3) RP ID とオリジンの検証。`apps/auth-worker/wrangler.jsonc` の `vars` に `RP_ID` と `WEBAUTHN_ORIGIN` を分けて持たせてあり、アサーション中の `rpIdHash` と `clientDataJSON.origin` の双方をこれらと突き合わせる。WebAuthn の origin binding はフィッシング耐性の本体であり、ここを緩めると他の対策が無意味になる。(4) User Verification の要求と、`passkeys.backed_up` / `passkeys.aaguid` による認証器属性の記録。 |

| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

#### RR-19 の補足 —— 「レビューが無い」ではなく「あるように見える」（2026-10-25 実測）

RR-19 は「機械的な強制が無い」と書いているが、**実測するとそれより悪い。**
`gh pr list` でマージ済み PR 60 本の review を集計した結果:

|                                  | 件数           |
| -------------------------------- | -------------- |
| マージ済み PR                    | 60             |
| **何らかの review が付いている** | **60**（100%） |
| **実質的な自動レビューがあった** | **20**         |
| **実質的なレビューが無かった**   | **40**         |
| **`APPROVED` が付いた PR**       | **0**          |

内訳は `copilot-pull-request-reviewer` が 60 件、`chatgpt-codex-connector` が 19 件、
すべて `COMMENTED`。**ただし copilot の 60 件のうち 59 件はレビューではなく
quota 不足の通知である。**

```
Copilot was unable to review this pull request because the user who
requested the review has insufficient remaining quota.
```

**つまり GitHub の UI 上はすべての PR にレビューが付いているが、3 分の 2 は
「レビューできませんでした」という通知である。** 後から `gh pr view` で
review の有無だけを見た人は、全 PR がレビュー済みだと判断する。

これは本書が繰り返し扱ってきた「**宣言はあるが発動しない**」と同じ形で
（`docs/runbook.md` の #88 / #96 / #101 / #127）、**受容したリスクの実際の
大きさが、見た目より大きい**ことを意味する。

**Copilot の quota は設定で直せる。** 通知自身が直し方を書いており
（組織をレビューの課金ソースにする）、直れば `tanahiro2010` とは別 identity の
レビュアーが全 PR に 1 つ復活する。**全セッションが同一アカウントであることの
影響を受けない**ので、RR-19 の受容範囲を実質的に狭められる。user の操作が要る。

なお **Copilot / Codex が `APPROVED` を出せるかは未確認**である。出せるなら
public 化時に `required approvals` を満たせる可能性があるが、**確かめていないので
前提にしないこと。** 現時点で 60 本中 `APPROVED` は 0 件という事実だけがある。

#### RR-19 の補足 2 —— 機械的なバックストップは**ゼロではない**（2026-10-28 実測、#58）

#58 は「レビューは完全に社会的な制御で、**バックストップがゼロ**である」と
書いていた。public 化（#26）で ruleset を張れるようになったので、**いまは
正確ではない。** 実物を引いて確かめた:

```
name        main: require CI
enforcement active
conditions  ~DEFAULT_BRANCH
bypass      0 件          <- 誰も迂回できない
rules       deletion / non_fast_forward / required_status_checks(["CI"])
```

**`bypass_actors` が空である**ことが効く。管理者を含めて誰も迂回できないので、
**CI が落ちているものは main に入らない。**

##### ただし、守っているのは「壊れていないこと」であって「正しいこと」ではない

この区別が本題である。**ruleset が止めるのは壊れているものだけで、
「壊れていないが間違っている」ものは素通りする。**

同じ日に 2 件出た。**どちらも CI は全部緑だった。**

| 入りかけたもの                                                 | CI            | 止めたもの   |
| -------------------------------------------------------------- | ------------- | ------------ |
| #241 に別セッションの実装途中（#208）が 92 行混入していた      | 緑            | **レビュー** |
| #246 が nfc-worker の借りているスタイルシートを 404 にしていた | 緑（1155 件） | **レビュー** |

前者は「無関係なファイルが入っている」、後者は「**画面は描かれるが
スタイルが当たらない**」で、**どちらもテストが赤くなる形をしていない。**
後者に至っては、壊れる側の Worker のテストも、壊す側の Worker のテストも、
**それぞれ自分の Worker の内側で全部通っていた**（§4.4）。

> **status check が守るのは「検査が通ること」であって「検査が正しいものを
> 見ていること」ではない。** 前者は機械が強制できるが、後者を増やす唯一の
> 手段がレビューであり、そこは依然として慣習だけで支えられている。

##### 残っている穴

- **formal Approve は構造的に出せない。** 全セッションが同一アカウント
  （`tanahiro2010`）なので GitHub が `Can not approve your own pull request`
  で拒否する。プランにも可視性にも依らない。したがって ruleset に
  `required approvals` を足すと**誰も満たせずマージが永久に止まる**（#58）
- **ruleset は PR を要求していない。** 入っている rule は `deletion` /
  `non_fast_forward` / `required_status_checks` の 3 つで、`pull_request` は
  無い。「PR を経由する」「出した本人以外がマージする」は**どちらも取り決め
  だけ**である
- **main への直 push が実際に止まるかは確かめていない。** status check が
  必須なので止まるはずだが、**確かめるには main へ push することになる**ので
  試していない。止まる前提で運用しないこと

##### 受容の形

**(A) 機械的なバックストップ**は入った —— CI を通らないものは main に入らない。
**(B) レビューの強制**は入らない。構造的に不可能なので、**慣習で支える範囲が
残ることを受け入れる**。

受け入れる根拠は、**残った範囲に効く手段がレビューしかなく、そのレビューが
実際に機能している**ことである（上の 2 件はどちらもレビューで止まった）。
機能しなくなったときに気づける指標は無い —— **止まった件数は数えられるが、
止まらなかった件数は数えられない。** そこが受容の中身である。

| `Date.now()` の分解能 | **1 ms**（200 ms の間に観測できた相異なる値が 201 個） |
| D1 の `select` 1 回   | **約 0.5 ms**（1,000 回の平均）                        |

**塞ぎたい差が、計測の最小単位より小さい。** 1 回の書き込みを応答経路から
外したかどうかは、1 ms 刻みのタイマーでは原理的に見えない。つまり
時間を測るテストは**差があっても無くても緑になる**。これは #122 で
見つかった「`SELF.fetch` に壊れた env を注入できていなかった」
resilience テストと同じ失敗の形である
（#122 で見つかった「壊れた env を注入できていなかった」resilience テストと
同じ失敗の形）。代わりに (a) 書き込みが**永久に解決しなくても応答が返ること**、
(b) 実在しないトークンと失効済みトークンで**待つ SELECT の回数が等しいこと**、
(c) **HTTP の入口が実際に `ctx.waitUntil` を呼んでいること**の 3 つを固定している。
(c) が無いと、入口が渡し忘れたときに UseCase 側だけ直って応答時間は元のまま、
という状態を検出できない。

### 4.4 検査の設計について —— 独立した面を 1 つ持つ

**本書の他の節と性質が違う。** ここに書くのは脅威でも緩和策でもなく、
**「対策が入っていることを、どうやって確かめ続けるか」**の話である。

このリポジトリで繰り返し出た壊れ方は、**対策が間違っていた**のではなく
**対策が効いていないことに気づけなかった**ほうが圧倒的に多い
（#88 / #96 / #122 / #132 / #141 / #143 / #151 / #164）。

**本節は検査を書くときの話で、§4.5 は書いた検査を確かめるときの話**である。
読む場面が違うので分けてある ——
本節は「この検査で足りているか」と思ったとき、
§4.5 は「戻したのに落ちなかった」と目の前で起きたときに読む。

#### 同じ面の中では矛盾が出ない

実際に踏んだものを並べると、形が 1 つに揃う。

|      | 見ていた面                     | 見えなかったこと                                         | 要った独立な面                            |
| ---- | ------------------------------ | -------------------------------------------------------- | ----------------------------------------- |
| #189 | nfc-worker の fake gateway     | auth-worker が `isAdmin` に嘘を返しても落ちない          | auth-worker から**実 D1** を見るテスト    |
| #196 | `hono/client` の型             | 型が**空**でも型検査は通る                               | 実行時の `app.routes`                     |
| #186 | HTTP の経路                    | 判定が片方の入口にしか無くても気づかない                 | **RPC の経路**から同じ入力を通す          |
| #196 | `app.routes` の重複            | 「ハンドラ 2 つの 1 ルート」と「2 回登録」が区別できない | （無い。**検査を取り下げた**。#195）      |
| #143 | `/health` の resilience テスト | `SELF.fetch` に壊れた env を注入できていなかった         | `createApp()` + 自前の `ExecutionContext` |
| #216 | `pnpm test` / `pnpm build`     | npm スクリプトが生成物を先に作るので、依存が隠れる       | **`wrangler deploy` を直接呼ぶ**経路      |
| #217 | `createApp().fetch()`          | Cloudflare の route 解決を一度も通らない                 | **本番の URL を実際に叩く**               |

**どれも「その面の中では何も矛盾しない」。** fake は仕様どおりに動き、
型検査は通り、HTTP のテストは緑で、`app.routes` は正しい内容を返す。
**嘘をついている部品が 1 つも無いのに、全体としては確かめたいことを
確かめていない。**

> **「fake が悪い」「型が弱い」ではない。** 検査の対象と検査の手段が
> 同じ面に乗っていることが問題である。

#### 本番だけが通る経路は、検査の外に残りやすい

表の下 2 行は同じ日に出た（2026-10-25）。**どちらも「本番でしか通らない
経路」を検査が踏んでいない**形で、他の行とは出方が違う。

- **#216**: `pnpm test` も `pnpm build` も npm スクリプト経由なので、
  **生成物が先に作られる。** CI の deploy は `pnpm exec wrangler deploy`
  を直接呼ぶので、そこだけが「生成が走っていない」状態に当たり、
  **本番デプロイだけが落ちた。** 検査は全部緑だった
- **#217**: Workers route の `/*` は裸の接頭辞を拾わない。
  `auth.under18.dev/account/*` は `/account/` を拾うが `/account` を
  拾わず、**利用者が URL バーに打つほうが 404 になっていた。**
  Worker 側の `strict: false`（#198）では直らない ——
  **リクエストが Worker に届いていない。** `createApp().fetch()` を
  叩くテストは route 解決の手前から始まるので、永久に気づけない

**共通するのは、その経路が「自分たちのコードの外」にあること。**
npm スクリプトと `wrangler` の間、Cloudflare の route 解決と Worker の
間 —— どちらも**こちらが書いていない層**で、テストは自然とその内側に
閉じる。

> **「ローカルで全部通る」は、ローカルに来る経路について言っている。**

足せる面は 2 つある。**実際の入口を叩くこと**（デプロイ後に本番の URL を
踏む）と、**設定そのものを読んで突き合わせること**
（`scripts/check-route-patterns.mjs`、`test/route-config.test.ts`）。
前者は遅いが本物で、後者は速いが「設定がそう書いてある」までしか言わない。
#217 では両方入れた。

#### 独立な面が無いときは、弱い形で残さず取り下げる

表の 4 行目だけは**独立な面が見つからなかった。** `app.routes` には
「`.get(path, middleware, handler)` と書いた 1 ルート」と「同じパスを
2 回登録した」を区別する情報が無く、どちらも 2 行積まれる。

そこで #195 では、検査を弱めて残すのではなく**アサーションごと消した。**
主張の範囲が間違っていたのだから、直せないなら取り下げるほうが正しい。

**欠陥のある検査を残すと、「ここは見ている」という誤った安心が残る。**
次に重複を疑った人は、その検査があることを理由に調べないほうへ倒れる。
**検査が無いほうが、少なくとも「見ていない」ことは正しく伝わる。**

#### 書くときの問い

新しい検査を足すとき、**「これは対象と独立した面から見ているか」**を
1 回問う。独立していないなら、たいてい次のどれかになっている。

- 実装が使う fake を、その実装のテストでも使っている
- 型で守っているものを、型検査だけで確かめている
- 1 つの入口で確かめた判定が、他の入口にもあると仮定している
- ある構造の性質を、同じ構造から導いた値で判定している

#### レビューは「面を増やす操作」である

面を増やす手は、検査を書き足すことだけではない。**別の人に見てもらうのも
面を 1 つ増やす操作である。**

> **レビュアーが有用なのは注意深いからではなく、別の面に立っているから。**

§4.5 に並べた 6 件のうち、**自分では見つからなかった 3 件はすべて、
指摘した側が別の作業をしていて、その作業の面から見えたもの**だった。
注意力の差ではない —— **自分が思いつかなかった壊し方を自分で思いつく**
必要がある側と、**別の作業をしていたら目に入った**側の差である。

だからレビューは、**検査を 1 本足すのと同じ列に並ぶ**。「念のため人に
見てもらう」ではなく、他の手段では増やせない面を増やしている。

これは **RR-19（レビューの機械的強制が無い）と #58** の根拠でもある。
役割分担だけが歯止めになっている状態は、**ある種類の壊れ方に対して
唯一効いている手段を、慣習だけで支えている**ということになる。

**その「ある種類」が何かは、§4.2 の「RR-19 の補足 2」で切り分けてある。**
ruleset（2026-10-28）が止めるのは**壊れているもの**だけで、**壊れていないが
間違っているもの**は素通りする。面を増やす手段が要るのは後者で、そこに
効くのはいまのところレビューだけである。

### 4.5 ネガティブ確認の実務 —— 落ちなかったときに何を疑うか

**§4.4 は検査を書くときの話で、本節は書いた検査を確かめるときの話**である。

**「戻すと落ちる」を試すこと自体は習慣になっている。** 難しいのは、
**戻したのに落ちなかったとき**に何を疑うかのほうで、ここを一律に
「検査が甘い」と読むと**壊れていないものを塞ぐためにテストが増える。**

#### ネガティブ確認にも軸の網羅が要る

習慣になっているだけでは足りない場面が 2 つ出た。

1. **壊し方が適用されていなかった。** prettier が整形した後の文字列と
   置換パターンが一致せず、**何も変えないまま「落ちないから OK」**と
   読みかけた（#173）。以後、置換が当たったことを出力させてから走らせる。
2. **壊し方の種類が足りなかった。** #196 のネガティブ確認は 4 件とも
   **ルートの増減**しか試しておらず、「同じルートを 2 回登録する」を
   試していなかったので、重複判定の欠陥が通った。

#201 は 2 の別の形で、**壊し方は当たっていたのに、どのテストもそこを
見ていなかった。** `purpose` を `signup` から `login` に変えても落ちない:

- 「登録済みにコードを作らない」は `findActive(REGISTERED, "signup")` を
  見ているので、`login` のチャレンジができても `signup` 側は null のまま
- 未登録アドレスでは `login` のコードがそもそも送られないので、他も落ちない
- 結果、**`purpose` を直接見ているテストが 1 つも無かった**

**3 つが別々の理由で素通りしている。** 1 つずつ見ると「そのテストは
別のことを見ているので当然」なのに、**合わせると誰も見ていない。**

**1 は手順の問題、2 は網羅の問題で、塞ぎ方が違う。**

- **1 は出力で塞げる。** 置換が当たったことを毎回出力させてから走らせる。
  機械的に守れる。
- **2 は出力では塞げない。** 「この検査が守ると主張している性質は、
  何通りの壊れ方をするか」を数える作業になる。**検査を書いた人が
  自分の主張の範囲を見積もる**ほかに手が無い。

後者が難しいのは、**壊し方を思いつけなかったものは、思いついていない
ことにも気づけない**ためである。だから上の「独立した面」のほうが効く
—— 面を 1 つ足すと、思いつかなかった壊れ方のいくつかが**自動的に**
見えるようになる。

#### 落ちなかったときに、まず疑う順番

1 と 2 の手前に、**もう 1 つ数え落としていた形がある。**

> **その「壊し方」は、本当に壊しているのか。**

#209 で `hc<T>(base)` の `base` の末尾にスラッシュを足したところ、
ネガティブ確認は**落ちなかった。** 検査が甘いのだと読みかけたが、
実際に組み立てられる URL を見ると:

```
http://localhost          => /account/api/me/sessions/x
http://localhost/         => /account/api/me/sessions/x
http://localhost/account  => /account/account/api/me/sessions/x   ← 壊れる形
```

**`hc` が末尾スラッシュを正規化していた。** 落ちなかったのは検査の
問題ではなく、**その入力では壊れていない**からである。

だから「戻しても落ちない」と出たときは、次の順で見る。

1. **壊し方が適用されたか。** 出力で確かめる（上の 1）
2. **適用した結果、挙動が実際に変わったか。** 変わっていないなら、
   それは壊し方ではない
3. **変わったのに落ちないなら、そこで初めて検査の問題。** 題材が
   悪いのか（#204）、軸が足りないのか（#196）を分ける

**2 を飛ばすと、壊れていないものを塞ぐためにテストを足すことになる。**
増えた分だけ、次に読む人が「ここは守られている」と受け取る範囲が
実態からずれる。

##### その手前 —— そもそも何かを見たのか

上の 1 の、さらに手前に来る形がある。**検査が 0 件を調べて「問題なし」
と報告する。**

#217 の `check-route-patterns.mjs` は、最初の版がこう出していた。

```
route patterns: 0 checked, every /* has its bare prefix
```

`unstable_readConfig` が env 解決済みの形しか返さず `config.env` が
空だったので、**pattern を 1 つも拾えていなかった。** 文面は成功に
見えるし、終了コードも 0 である。

**「落ちなかった」より質が悪い。** ネガティブ確認は「戻したのに
落ちない」で異常に気づけるが、**0 件の検査は戻しても落ちないのが
正常な顔をしている。** 何を戻しても同じ出力になる。

対処は、**0 件を異常として落とすこと。**

```js
if (all.size === 0) {
  console.error("::error::No route patterns were found … This is a bug in the check.");
  process.exit(1);
}
```

**「このリポジトリには対象が実在する」と分かっている検査は、0 件を
正常と見なしてはいけない。** 同じ注意が `check-service-bindings.mjs` と
`scripts/lib/bucket-visibility.mjs`（印が無ければ `unknown`）にもある。

件数を出力すること自体も効く —— **`0 checked` と書いてあったから
気づけた。** 「問題なし」とだけ出していたら分からない。

#### 出どころ —— どちらの段かで、気づける人が変わる

上の 1 と 2 がどう見つかったかを並べると、**出どころが分かれる。**

| 見つかったもの                | どちらの段 | きっかけ                  |
| ----------------------------- | ---------- | ------------------------- |
| #176 の窓の境界に届いていない | 1（手順）  | 自分で出力を見た          |
| #188 の置換が当たらない       | 1（手順）  | 自分で出力を見た          |
| #188 の構文エラー             | 1（手順）  | 自分で出力を見た          |
| #196 の重複判定               | 2（網羅）  | #195 を書いていた別の担当 |
| #195 の末尾スラッシュ         | 2（網羅）  | 別の担当                  |
| #188 の「以後に足すルート」   | 2（網羅）  | 別の担当                  |

**1 は全部自分で塞げている。2 は 1 つも自分で見つかっていない。**
段の違いがそのまま「自分で塞げるか」に対応した。

**この 6 件に限れば、である。** 下の「例外」のとおり、2 でも**数え上げ
れば自分で見つかる**ことがある。表が言えるのは「**思いついて気づいた
2 は 1 件も無い**」までで、「2 は自分では無理」ではない。

これは偶然ではない。**2 を自分で見つけるには、自分が思いつかなかった
壊し方を自分で思いつく必要がある**からで、それができるなら最初から
書いている。**別の面に立っている人のほうが先に見える** ——
§4.4 の「レビューは面を増やす操作である」はここから来ている。

#### 例外：数え上げれば自分でも見つかる

**自分で見つけた網羅漏れが 2 件ある。どちらも数え上げて出た。**

- **#204**: 戻し方を 9 通り表に並べて機械的に全部走らせたところ、
  **2 通りが「戻しても落ちない」**と出た。テストの題材が悪く、戻した
  実装でも同じ答えになっていた
- **#201**: 戻し方を 3 通り試して、**1 通りが落ちなかった**
  （`purpose` を `signup` → `login`）。上に書いた 3 つの理由が重なって
  素通りしていた

**どちらも思いついて見つけたのではなく、数えて見つけた。** 上で
「2 は出力では塞げない」と書いたのは**1 件ずつ試す限りで**の話で、
**戻し方を先に表にしてから走らせると、出力で塞げる側に寄る。**

表にすることが効くのは、**1 件ずつだと「落ちた」で満足して次へ行く**
からである。並べると「落ちなかった行」が目に入る。

ただしこれは**思いついた壊し方の中での取りこぼし**を潰すだけで、
**表に載らなかった壊し方には何もしない。** 面を増やすほうの代わりには
ならない。
